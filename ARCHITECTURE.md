# Архитектура DONARIUM

DONARIUM — персональная библиотека цифровых моделей. Один процесс Node.js обслуживает React-интерфейс, API, файловые потоки и ограниченные фоновые операции. PostgreSQL хранит метаданные; оригиналы остаются обычными файлами. Регистрации, пользователей, ролей, организаций и облачных зависимостей нет.

## Что установлено аудитом

Исходный проект уже имел TypeScript monorepo, React/Vite, Fastify, PostgreSQL-схему с индексами, чтение каталога, поиск и серверную пагинацию. Переписывать этот каркас не потребовалось.

Основные пробелы были функциональными: API только для чтения; шесть демонстрационных записей вместо рабочей библиотеки; обязательный SKU; отсутствие связи относительных путей с файловой системой; отсутствие загрузки, ZIP, импорта папок и переносимого восстановления. Отдельный интерфейс личного пространства сохранял избранное, коллекции, профиль и историю в localStorage, поэтому его JSON-экспорт не представлял серверную библиотеку. Многопользовательской БД или серверной авторизации не было.

Локальные профили, коллекции, активность и связанные экраны/модули удалены из рабочего интерфейса. Главная рабочая область — реальный каталог. Демонстрационные данные сохранены только как явно выбранный режим `DATA_MODE=demo` и тестовые fixtures: этот режим не пишет в БД и не подменяет недоступный PostgreSQL. Старые пользовательские localStorage-данные не удаляются скриптами, но больше не используются.

## PostgreSQL

| Таблица | Содержание и связи |
| --- | --- |
| `products` | UUID, nullable уникальный SKU, название, описание, статус `ready`/`processing`, даты, обложка; legacy URL изображения/источника сохраняются |
| `categories`, `product_categories` | Категории и связь многие-ко-многим; схема поддерживает родительскую категорию |
| `tags`, `product_tags` | Теги и связи; уникальность имени тега без учёта регистра |
| `storage_locations` | Стабильный UUID, ключ и имя хранилища; физических абсолютных путей здесь нет |
| `assets` | Файловая связь: UUID, товар, тип, имя, MIME, размер, необязательный SHA-256, версия, дата, `origin` и путь либо HTTP(S) URL |
| `import_sources` | Уникальная пара «хранилище + папка» → карточка для повторного импорта |
| `external_links` | Независимые идентификаторы внешних систем; существующие данные сохранены, подключения к БД магазина нет |
| `transfer_receipts` | Результат завершённого восстановления, записанный в одной транзакции с каталогом |
| `schema_migrations` | Имена, SHA-256 и даты применённых миграций |

Один физический файл можно привязать к нескольким карточкам; повторная связь того же пути с той же карточкой запрещена индексом. Это связь цифрового ресурса, без навязанной модели интернет-магазина.

Миграции:

1. `001_initial.sql` — исходная схема; файл не изменялся.
2. `002_library.sql` — nullable SKU, статус, обложка, происхождение ресурсов, источники импорта и уникальность связей. Вычисляемые поисковые колонки пересоздаются с `coalesce(sku, '')`; пользовательские записи сохраняются.
3. `003_restore_timestamps.sql` — сохранение исходного `updated_at` при восстановлении через локальную настройку транзакции, индекс `lower(title)`.
4. `004_transfer_receipts.sql` — подтверждение COMMIT восстановления для обработки прерывания процесса.
5. `005_asset_location_lookup.sql` — индекс поиска существующих файловых связей при импорте папки.

CLI применяет каждый файл транзакционно под advisory lock и отказывается от изменённого checksum уже применённой миграции. До `002` выполняется проверка дублирующих файловых связей: при наличии дублей runner останавливается для ручного разбора, ничего не удаляя. Нужны `DB_MIGRATION_CONFIRM=donarium` и отдельная БД с именем `donarium`/`donarium_<suffix>`. Рабочие миграции не запускаются автоматически при старте API. Процедура backup и диагностика дублей: [docs/BACKUP.md](docs/BACKUP.md).

## Каталог и согласованность

CRUD работает через `/api/v1/products`; категории — `/api/v1/categories`. Редактирование товара и замена его категорий/тегов выполняются атомарно. Обложка должна быть изображением, принадлежащим этой карточке. Удаление карточки каскадно удаляет связи в БД, но не физические файлы. Отвязка ресурса также сохраняет оригинал.

`GET /api/v1/products` принимает `q`, `category`, `tag`, `status`, `sort`, `page`, `pageSize`. Поиск охватывает название, SKU, описание и теги, поддерживает частичные совпадения, кириллицу и латиницу. PostgreSQL использует `simple` full-text и `pg_trgm`; SQL параметризован, символы LIKE экранируются. Есть индексы для поиска, связей, дат, статуса и сортировки по имени. Стабильный UUID используется для дополнительного порядка результатов. Размер страницы ограничен 100, весь каталог на клиент не загружается. Frontend сохраняет фильтры в URL и применяет debounce.

## Файлы и защита

`STORAGE_ROOTS` задаёт JSON-массив разрешённых внешних корней с ключом, именем и абсолютным путём. `STORAGE_ROOT` — совместимый вариант одного корня `LIBRARY`. Внешние оригиналы используются только для чтения. Ключ `DONARIUM_UPLOADS` зарезервирован для управляемого каталога `MANAGED_STORAGE_ROOT`; `WORK_ROOT` содержит временные операции переноса. Оба последних каталога должны быть доступны процессу на запись и сохраняться между перезапусками.

Браузер выбирает корень по ключу и работает с относительными путями. Backend запрещает абсолютные пути, `..`, `.` и пустые компоненты, обратные слеши, управляющие символы и символические ссылки. На Ubuntu открытие выполняется последовательно относительно уже открытых дескрипторов директорий через `/proc/self/fd` с `O_NOFOLLOW`; подмена компонента пути не перенаправляет чтение за разрешённый корень. Принимаются обычные файлы и директории, системные специальные файлы не выдаются.

Файловые корни не находятся в публичной статической директории. Загрузка и скачивание потоковые; файл целиком в RAM не читается. Прямой download и ZIP карточки проходят через авторизованный API. Отсутствующие и недоступные оригиналы отражаются отдельным статусом. Исправление связи выполняется отвязкой и повторным выбором файла; автоматического поиска перемещённых файлов нет.

Каталог запрашивает WebP-миниатюры до 480×480 через `sharp`, с ленивой загрузкой изображений. Ограничены число одновременных преобразований (2), очередь (100), входное изображение (80 млн пикселей) и кэш результатов (256). Оригинальные изображения не перезаписываются.

## Импорт папок

Сканирование возвращает ID фоновой задачи. Кандидатом становится папка с поддерживаемой моделью, проектом или архивом; изображения и документы в этой папке включаются в набор файлов. Название берётся из имени папки, обложка выбирается по имени `cover`/`preview`/`front`/`обложка` либо из первого изображения. Архивы не распаковываются, содержимое 3D-проектов не анализируется.

Список форматов моделей и архивов общий с выбором файла фигурки: `FIGURE_FILE_EXTENSIONS` в `packages/shared/src/index.ts`, включая MAX, TAR и GZ. Регистрация логического корня выполняется общей функцией `location` из `registry.ts`.

До подтверждения пользователь выбирает карточки и при необходимости общую категорию. Новые карточки получают статус `processing`. Каждая папка импортируется в собственной транзакции; повторный импорт по `import_sources` обновляет связи существующей карточки. Новые ссылки добавляются, исчезнувшие оригиналы не удаляются, отредактированные названия/описания сохраняются. Итог содержит созданные/обновлённые/пропущенные записи и ошибки.

В процессе допускается одна операция папочного импорта; preview хранится в памяти, после рестарта нужно повторить сканирование. Ограничения: глубина 50, 200000 просмотренных элементов, 10000 кандидатов и 10000 поддерживаемых файлов в одной папке, 20 активных preview. Ответы preview пагинируются. Одна директория читается через `readdir` целиком: очень широкие каталоги следует разделять на вложенные папки. Браузер файлов отдельно ограничивает директорию 100000 элементами. Отмена разрешена до подтверждения.

## Перенос и восстановление

JSON/CSV выдаются потоками из согласованного снимка PostgreSQL с курсором по 500 строк. Полный ZIP формируется фоновой задачей на диске; в память не помещается весь архив или тяжёлый файл. Перед включением локального файла вычисляется SHA-256, а при чтении в ZIP проверяется, что содержимое не изменилось. Неисправная локальная связь прерывает полный экспорт.

Восстановление разделено на загрузку, проверку, preview и явное подтверждение `skip`/`copy`. Архив распаковывается в закрытый staging внутри управляемого хранилища; пути, таблицы, IDs, ссылки, размеры и SHA-256 проверяются до записи каталога. После подтверждения метаданные восстанавливаются в одной транзакции, файлы перемещаются в `restored/<job-id>`, затем вместе с данными фиксируется receipt. При обычной ошибке до COMMIT транзакция откатывается, перемещённые файлы возвращаются в staging. После прерывания процесса receipt отличает завершённый импорт от незафиксированного перемещения; служба сверяет его при запуске.

Состояния переноса сохраняются в `WORK_ROOT`; допускается одна операция, максимум 100 записей задач. Задания старше суток очищаются при запуске, завершённые можно удалить через UI. Подробная спецификация и границы восстановления: [DATA_PORTABILITY.md](DATA_PORTABILITY.md).

## Пароль и эксплуатация

В режиме PostgreSQL обязателен `ADMIN_PASSWORD` длиной от 12 символов. Пароль сравнивается через scrypt и constant-time comparison; регистрации и пользовательской БД нет. Случайная cookie `HttpOnly; SameSite=Strict` действует 12 часов, сеансы хранятся в памяти и завершаются после рестарта. `SECURE_COOKIE=true` применяется при HTTPS. Есть ограничение попыток входа, проверка Origin для операций записи, CSP и запрет встраивания. `/health` доступен для локальной проверки состояния, данные каталога и файлов требуют входа.

Развёртывание — локальное. Compose публикует порт приложения на настроенном `HOST`, PostgreSQL — на loopback. Настройки firewall, роутера, публичные прокси и инфраструктура SKUFnya приложением не изменяются. Внешние каталоги следует монтировать read-only; управляемое и временное хранилища — отдельно на запись. Настройки корней меняются через окружение с перезапуском, веб-настройки показывают состояние.

Ограничения производительности управляются без отдельной инфраструктуры: пул PostgreSQL до 5 подключений, одна папочная операция, один перенос, два скачиваемых ZIP карточек. Фоновые задачи выполняются в процессе Node.js с асинхронным I/O; тяжёлая обработка изображений — в `sharp`. Большой экспорт требует диска под дополнительную копию файлов, проверка SHA-256 добавляет чтение оригиналов. Серверная пагинация использует OFFSET; для очень дальних страниц при сотнях тысяч карточек следующим полезным улучшением будет keyset pagination.

При сканировании уже вручную связанных файлов одна подходящая карточка безопасно принимается как существующая; неоднозначность и источник другой папки блокируют создание дубликата. Решение повторно проверяется в транзакции при подтверждении.
