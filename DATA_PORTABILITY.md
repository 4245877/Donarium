# Формат обмена Donarium v2

Текущий формат экспорта — v2; импорт поддерживает v1 и v2. Для большой библиотеки .141 основной переносимый backup через интерфейс — **ZIP метаданных без оригиналов**. Физические файлы резервируются отдельно на другой носитель. [Инструкции хранилища](docs/LOCAL_STORAGE.md) · [Backup](docs/BACKUP.md).

## Текущий JSON и CSV

`GET /api/v1/exports/catalog.json` выдаёт `format: donarium-metadata`, `version: 2` и 12 таблиц: products, categories, tags, product_categories, product_tags, assets, external_links, storage_files, import_sources, storage_operations, storage_matches, storage_events. Это метаданные с UUID, логическими ключами и относительными путями, без байтов оригиналов. CSV остаётся табличным представлением товаров. Произвольные JSON/CSV через UI не импортируются; для восстановления используйте ZIP.

## ZIP v2

`POST /api/v1/exports/metadata` создаёт задачу ZIP без оригиналов; `POST /api/v1/exports/archive` — ZIP с файлами. Состояние: `GET /api/v1/transfers/:id`, скачивание: `/api/v1/transfers/:id/download`. Интерфейс показывает длительные операции.

ZIP содержит manifest.json и по NDJSON на каждую из 12 таблиц. Manifest имеет `format: donarium`, `version: 2`, `fileMode: metadata|files`, createdAt и для каждой таблицы count/SHA-256. В metadata-режиме у реестра `archive_path: null`; file_id, storage_key, relative_path, размер и SHA-256 сохраняются. В files-режиме оригинал находится в `files/<file-uuid>/<name>`; один registry file включается один раз, независимо от числа связей с товарами. Разные физические оригиналы, даже с одинаковым SHA-256, автоматически не удаляются и не объединяются.

assets.file_id ссылается на storage_files.id. Размеры представлены десятичными строками. Экспорт включает источники импорта и историю сопоставления; пароль владельца, сеансы и абсолютные пути конфигурации хранилищ не включаются. Исторические метаданные происхождения могут содержать старые пути/URL как сведения об импорте.

Полный ZIP и загрузка ZIP для восстановления ограничены 4 ГиБ. Создание полного 394-ГиБ ZIP в текущей установке отклоняется; используйте metadata ZIP и независимую копию файлов. В production проверен metadata ZIP размером 970019 байт с 598 товарами и 2427 файлами.

## Восстановление v2

`PUT /api/v1/restores/preview` принимает ZIP; проверяются безопасные пути, SHA-256 таблиц/файлов, UUID и все ссылки. Предпросмотр показывает конфликты и недоступные оригиналы. `POST /api/v1/restores/:id/confirm` с conflict=skip|copy применяет проверенные данные транзакционно. Старые товары не перезаписываются; режим copy создаёт новые UUID товаров, переиспользуя файлы. При совпадающем UUID файла и конфликтующем содержимом восстановление останавливается без перезаписи оригинала.

Метаданные можно восстановить до подключения .141: файлы будут unavailable, а UUID, логические ключи и относительные пути сохранятся. После подключения прежних ключей LIBRARY/DONARIUM_UPLOADS/INVENTORY выполните проверку целостности. Для библиотеки доступен приём SHA-256, вычисленных на .141, с точным сопоставлением размера, mtime и ctime через NFS; наносекунды хранятся строками без округления. Загруженные файлы проверяются потоковым SHA-256. Изменённые файлы отмечаются corrupt с сохранением ожидаемой контрольной суммы.

28 октября свежий ZIP 970019 байт восстановлен в отдельной тестовой схеме: сохранены все 598 UUID товаров, 2416 UUID вложений, 2427 UUID файлов, пути, контрольные суммы и связи. Временные файлы проверки находились в tmpfs; оригиналы не копировались. Для переноса на другой сервер подключите тот же .141, настройте NFS exports/firewall под новый IP и STORAGE_GUARDS под новые пути; UUID и относительные пути в карточках не изменяйте. Полный host-backup теперь проверяет NFS-корни и запрещает системную ФС как назначение — см. docs/BACKUP.md.

Ниже сохранена спецификация старого v1 для чтения исторических архивов. Она не описывает текущий GET JSON или экспорт v2.

# Исторический формат v1 (поддерживается для восстановления)

Библиотека читается независимо от приложения: метаданные представлены JSON/CSV, оригиналы — обычными файлами в ZIP. Для обратного импорта через UI используется **полный ZIP DONARIUM**, содержащий манифест, семь таблиц NDJSON и локальные файлы. Обычный JSON/CSV не является резервной копией PostgreSQL и не загружается в этот импортёр.

[Архитектура](ARCHITECTURE.md) · [Полный backup PostgreSQL и хранилищ](docs/BACKUP.md)

## JSON метаданных

`GET /api/v1/exports/catalog.json` возвращает UTF-8 JSON:

```json
{
  "format": "donarium-metadata",
  "version": 1,
  "createdAt": "2026-10-24T10:00:00.000Z",
  "products": [],
  "categories": [],
  "tags": [],
  "product_categories": [],
  "product_tags": [],
  "assets": [],
  "external_links": []
}
```

Это полный структурированный снимок метаданных с UUID, связями, описаниями, статусами, датами и внешними ссылками. У локальных assets сохраняются ключ хранилища `storage_key` и относительный `relative_path`; физические абсолютные пути корней и секреты подключения не экспортируются. Большие размеры файлов представлены десятичными строками. Массивы выдаются потоково в согласованной PostgreSQL-транзакции, курсор читает по 500 строк. Тяжёлые файлы в JSON не включаются.

## CSV

`GET /api/v1/exports/catalog.csv` — один CSV UTF-8 с BOM и CRLF. Столбцы:

```text
id,sku,title,description,status,categories_json,tags_json,assets_json,cover_asset_id,created_at,updated_at
```

Все ячейки заключены в двойные кавычки; вложенные кавычки удваиваются. `categories_json`, `tags_json` и `assets_json` содержат явные JSON-массивы, без неоднозначного разделения тегов запятыми. В категориях сохраняются `id`, `slug`, `name`; в тегах — `id`, `name`; в ресурсах — `id`, `name`, `storage_key`, `relative_path`, `external_url`. UUID обложки связывает её с ресурсом.

CSV предназначен для обычных табличных редакторов и сторонних обработчиков. Строки, начинающиеся с `=`, `+`, `-`, `@`, tab или CR, получают ведущий апостроф для предотвращения исполнения формул таблицей. Поэтому для точного переноса исходных строк используйте JSON или полный ZIP. Файловые байты в CSV не включаются.

## Полный ZIP

Создание начинается через `POST /api/v1/exports/archive` и возвращает задачу. Её состояние доступно по `GET /api/v1/transfers/:id`, результат — `/download`. Веб-раздел «Экспорт и восстановление» выполняет эти действия и показывает статус.

```text
donarium-library.zip
  manifest.json
  products.ndjson
  categories.ndjson
  tags.ndjson
  product_categories.ndjson
  product_tags.ndjson
  assets.ndjson
  external_links.ndjson
  files/
    <asset-uuid>/
      <original-name>
```

ZIP64 позволяет работать с большими архивами. Директории выше показаны для понимания структуры; ZIP содержит записи файлов без отдельных записей директорий. Исходные байты локальных файлов не изменяются и не сжимаются; метаданные могут быть сжаты. Путь с UUID ресурса предотвращает конфликт одинаковых имён файлов.

Оригиналы включаются независимо от того, были они загружены через DONARIUM или привязаны из внешнего разрешённого корня. `storage_key` и `relative_path` локального ресурса заменяются на `archive_path`, не содержащий расположения исходного сервера. Хранилища, сеансы, пароль владельца, журналы задач и `import_sources` в переносимый формат не входят.

HTTP(S)-ресурсы из `external_url` сохраняются как ссылки: сервер не скачивает их содержимое. Legacy `image_url` и `source_url` также остаются ссылками. Для включения фотографии в архив она должна быть локальным asset типа `image`; URL произвольной внешней фотографии сам по себе не создаёт вложение. Примерные иллюстрации приложения не копируются как пользовательские оригиналы.

Полный экспорт прекращается с ошибкой, если локальная связь отсутствует, недоступна или выходит за разрешённый корень. До экспорта нужно исправить или отвязать её. Система не создаёт молча неполный архив. SHA-256 вычисляется потоково, при включении файла в ZIP проверяется повторно: изменившийся во время экспорта файл делает операцию неуспешной.

### Манифест

```json
{
  "format": "donarium",
  "version": 1,
  "createdAt": "2026-10-24T10:00:00.000Z",
  "tables": {
    "products": { "count": 1, "sha256": "<64 lowercase hex characters>" },
    "categories": { "count": 0, "sha256": "<64 lowercase hex characters>" },
    "tags": { "count": 0, "sha256": "<64 lowercase hex characters>" },
    "product_categories": { "count": 0, "sha256": "<64 lowercase hex characters>" },
    "product_tags": { "count": 0, "sha256": "<64 lowercase hex characters>" },
    "assets": { "count": 1, "sha256": "<64 lowercase hex characters>" },
    "external_links": { "count": 0, "sha256": "<64 lowercase hex characters>" }
  }
}
```

Обязательны все семь таблиц, включая пустые. `count` — число записей. `sha256` — SHA-256 **точных байтов** соответствующего `.ndjson`, включая завершающие LF. Для пустого файла используется SHA-256 пустой строки. Хеши обнаруживают повреждение содержимого; цифровой подписи и подтверждения автора формата нет.

### NDJSON и поля

Каждая строка содержит один JSON-объект UTF-8 и завершается `LF`. Пустые строки допускаются. Переходы строк внутри значений кодируются JSON-экранированием. Файл не является JSON-массивом. Имена полей соответствуют SQL-схеме:

| Таблица | Поля |
| --- | --- |
| `products` | `id`, `sku` (строка или null), `title`, `description`, `status`, `cover_asset_id` (UUID или null), `image_url`, `image_alt`, `source_url`, `created_at`, `updated_at` |
| `categories` | `id`, `slug`, `name`, `parent_id` (UUID или null) |
| `tags` | `id`, `name` |
| `product_categories` | `product_id`, `category_id` |
| `product_tags` | `product_id`, `tag_id` |
| `assets` | `id`, `product_id`, `kind`, `name`, `media_type`, `size_bytes`, `sha256`, `version`, `external_url`, `created_at`, `origin`, `archive_path` |
| `external_links` | `id`, `product_id`, `system`, `external_id`, `url`, `metadata` (JSON-объект) |

UUID — постоянные идентификаторы. Даты — строки ISO 8601 с часовым поясом. Статус — `ready` или `processing`; `kind` — `image`, `model`, `archive`, `source`, `other`; `origin` — `external` или `uploaded`. Категории используют ASCII slug, а имя, теги и описания поддерживают Unicode.

У локального asset обязательны `archive_path`, десятичная строка `size_bytes` и SHA-256. Например:

```json
{"id":"11111111-1111-4111-8111-111111111111","product_id":"22222222-2222-4222-8222-222222222222","kind":"model","name":"dragon.stl","media_type":"application/octet-stream","size_bytes":"12345","sha256":"<64 lowercase hex characters>","version":null,"external_url":null,"created_at":"2026-10-24T10:00:00.000Z","origin":"external","archive_path":"files/11111111-1111-4111-8111-111111111111/dragon.stl"}
```

У внешней ссылки `external_url` содержит HTTP(S) URL без встроенных логина/пароля, `archive_path` равен null, размер и хеш могут быть null. Набор фотографий восстанавливается из assets с `kind=image`, основная фотография — по `cover_asset_id`.

Чтобы прочитать библиотеку сторонним скриптом, достаточно распаковать ZIP, проверить хеши из manifest, читать `.ndjson` построчно и соединять таблицы по UUID. Привязки файлов не требуют установленного DONARIUM.

## Проверка и восстановление

1. В разделе переноса выберите полный ZIP. `PUT /api/v1/restores/preview` принимает поток `application/octet-stream`.
2. Backend сохраняет ZIP в `WORK_ROOT`, распаковывает в закрытый `.restore-stage-<job-id>` внутри `MANAGED_STORAGE_ROOT` и проверяет данные. Каталог ещё не изменяется.
3. Preview показывает число сущностей и конфликтующих карточек. До подтверждения задачу можно отменить и удалить временные данные.
4. Выберите `skip` или `copy` и подтвердите импорт. `POST /api/v1/restores/:id/confirm` запускает восстановление; состояние и отчёт выдаются через `/api/v1/transfers/:id`.

Проверяются версия, разрешённые имена ZIP-записей, пути, размеры, хеши таблиц и оригиналов, поля строк, повторные IDs, наличие связанных сущностей и принадлежность обложки карточке. Запрещены traversal, абсолютные пути, обратные слеши, символические ссылки, специальные файлы, шифрованные ZIP-записи и повторяющиеся пути. Импорт не распаковывает вложенные пользовательские архивы: STL/ZIP/RAR внутри `files` остаются непрозрачными байтами.

Политики конфликтов:

| Ситуация | Поведение |
| --- | --- |
| Карточка без конфликта UUID/SKU | Сохраняет UUID и SKU |
| UUID или ненулевой SKU уже существует, `skip` | Пропускается вся импортируемая карточка вместе с её файловыми связями |
| UUID или SKU существует, `copy` | Создаётся новый UUID карточки, SKU становится null; связи переназначаются |
| Категория с совпавшим UUID или slug | Используется существующая; её название и организация сохраняются |
| Тег с совпавшим UUID или именем без учёта регистра | Используется существующий тег |
| UUID ресурса уже занят | Генерируется новый UUID, ссылка обложки переназначается |
| Конфликт `external_links` | Существующая запись сохраняется, конфликтующий внешний mapping не дублируется |

Повторный импорт с `skip` не создаёт повторные карточки. `copy` намеренно создаёт отдельные копии конфликтующих карточек и файлов. Восстановление переносимого архива не воссоздаёт старые `import_sources`: новое окружение не связано с исходными папками сервера.

Локальные файлы после восстановления находятся в `MANAGED_STORAGE_ROOT/restored/<job-id>/<source-asset-id>/<name>`, связаны с `DONARIUM_UPLOADS` и имеют `origin=uploaded`. Это принадлежность новому управляемому хранилищу, поэтому исходный `origin=external` может измениться. Байты и SHA-256 остаются прежними. Абсолютные пути нового сервера задаются его конфигурацией.

### Транзакции, даты и прерывание

Подтверждённый каталог восстанавливается в одной транзакции под advisory lock; категории, теги, карточки, связи, ресурсы и результат в `transfer_receipts` фиксируются вместе. Перемещение `stage/files` в `restored/<job-id>` происходит перед COMMIT и внутри того же управляемого файлового хранилища. При обычной ошибке SQL откатывается, а перемещение возвращается в staging. Оригинальные подключённые файлы не изменяются.

Миграция `003_restore_timestamps.sql` позволяет сохранить исходные `created_at`/`updated_at`, включая назначение обложки, без отключения ограничений целостности. Для обычного редактирования триггер продолжает обновлять `updated_at`.

Миграция `004_transfer_receipts.sql` добавляет receipt успешного COMMIT. После рестарта служба сверяет незавершённую задачу: при наличии receipt отмечает её завершённой; без receipt перемещённые файлы возвращаются в staging, задача получает статус ошибки. Это восстановление согласованности, не автоматическое продолжение импорта. Для повторной попытки загрузите архив заново. Храните исходный ZIP до проверки результата; не удаляйте временные каталоги вручную во время операции.

## Ограничения и стоимость диска

- В одном процессе одновременно выполняется одна задача полного переноса. JSON/CSV выдаются потоково отдельно.
- Размер загружаемого ZIP и суммарный распакованный размер ограничены `MAX_ARCHIVE_BYTES`: по умолчанию 2 TiB, допустимая настройка до 10 TiB. Для одиночной загрузки используется отдельный `MAX_UPLOAD_BYTES`, по умолчанию 20 GiB.
- До 2000000 ZIP-записей; манифест до 1 MiB; одна NDJSON-таблица до 256 MiB; одна JSON-строка до 1048576 символов. При превышении нужно разделить библиотеку или пересмотреть лимиты в коде.
- Проверка IDs/связей использует множества идентификаторов в RAM; файловые байты и таблицы читаются потоками. Это не импорт с постоянным объёмом памяти независимо от числа карточек.
- Полный экспорт занимает место под дополнительную копию локальных файлов и метаданные. Импорт временно хранит загруженный ZIP и распакованные файлы; при подтверждении staging переименовывается без ещё одной копии файлов. Конфликт `copy` сохраняет дополнительные оригиналы.
- SHA-256 требует чтения всего набора оригиналов; полный экспорт дополнительно читает их для ZIP. Для корректного снимка внешние файлы должны оставаться неизменными на время операции.
- До 100 записей задач переноса; завершённые/ошибочные задачи можно удалить через интерфейс. Удаление задачи очищает временные материалы, но сохраняет уже восстановленные файлы. Задачи старше суток очищаются при запуске, постоянного планировщика очистки нет.
- JSON/CSV не импортируются автоматически. Для PostgreSQL disaster recovery используйте `pg_dump` и копии всех хранилищ из [docs/BACKUP.md](docs/BACKUP.md).

Критичные проверки выполняются в `tests/transfer.test.ts` и `tests/portability.integration.test.ts`: вредоносные ZIP-пути, ссылки и повторы, ограничения парсинга, версия/хеши/связи, а также полный круговой перенос в отдельную пустую PostgreSQL-БД и изолированное хранилище. Фактические результаты конкретного запуска приведены в отчёте проверки проекта.
