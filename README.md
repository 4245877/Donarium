# DONARIUM

Независимый аудит 28.10.2026: [подтверждённые ошибки, исправления и ограничения](docs/INDEPENDENT_AUDIT_2026-10-28.md). Исправления подготовлены в исходниках и отдельном образе; обновление рабочего сервиса выполняется в согласованное окно. Для обслуживания используйте `systemctl disable --now donarium.service`: обычный stop не защищает от будущего OnFailure NFS mount.

Персональная self-hosted библиотека цифровых моделей и файлов: React + TypeScript, Fastify, PostgreSQL 16, файловое хранилище Ubuntu. Один владелец, один пароль, без регистрации и облачных сервисов.

Рабочая установка: **http://192.168.0.151:4180** (LAN), **http://100.91.30.10:4180** (Tailscale). Рабочий каталог использует PostgreSQL и реальные импортированные товары; демонстрационные карточки в него не переносились. Пароль владельца находится в локальном `.env`, поле `ADMIN_PASSWORD`; файл имеет права `0600` и не входит в Git. Библиотека, загрузки и рабочие файлы расположены на HDD сервера .141 и подключены по NFS. Управление доступно в разделе «Файлы». Статус внедрения и проверки восстановления: [отчёт](docs/STORAGE_IMPLEMENTATION_REPORT.md).

## Что работает

- Создание, просмотр, редактирование и удаление карточек; необязательный SKU, описание, категории, теги, статусы и фотографии.
- Поиск кириллицы/латиницы по названию, SKU, описанию и тегам, фильтры, сортировка, серверная пагинация, сохранение фильтров в URL.
- Привязка существующих файлов/папок без копирования, загрузка, галерея, миниатюры, потоковое скачивание и ZIP64, проверка отсутствующих файлов, отвязка.
- Сканирование вложенных папок в фоне, предварительный просмотр, выбор карточек и категории, подтверждение, отчёт, безопасный повторный импорт.
- Потоковые CSV и JSON; полный ZIP с метаданными и оригиналами; проверяемое восстановление с предварительным просмотром и разрешением конфликтов.
- Защита API и файлов паролем владельца, HttpOnly-сессия на 12 часов, ограничение попыток входа, проверка Origin при изменениях.

Удаление карточки и отвязка **сохраняют физические файлы**, включая загрузки DONARIUM. Большие файлы находятся на диске, PostgreSQL хранит только метаданные.

## Запуск существующей установки

```bash
cd /home/hpelitdesk/apps/Donarium
sudo systemctl start donarium.service
docker compose ps
curl -f http://192.168.0.151:4180/health
```

В рабочем `.env` COMPOSE_FILE включает `compose.nfs.yml`; systemd запускает приложение после четырёх NFS mounts. После изменения кода соберите отдельный образ, проверьте его и задайте DONARIUM_STORAGE_IMAGE; не исключайте NFS override при пересоздании app.

Остановка и журналы:

```bash
sudo systemctl stop donarium.service
docker compose logs --tail=100 app
```

Не добавляйте `down -v`: volume `donarium_donarium_postgres` содержит рабочую БД. Порт приложения публикуется на двух адресах из `.env`: `HOST=192.168.0.151` и `TAILSCALE_IP=100.91.30.10`, без wildcard-привязки. Если `TAILSCALE_IP` не задан, дополнительная привязка остаётся на loopback. PostgreSQL — только на `127.0.0.1:5548`. SKUFnya не используется. Проброс порта роутера и публикация в интернете не нужны.

На `miha` отдельный сервис `donarium-4180-firewall.service` загружает `/etc/ufw/donarium-4180.nft` до запуска Docker. Правила разрешают входящий TCP/4180 только из `192.168.0.0/24` через `eno1` к LAN-IP и из `100.64.0.0/10` через `tailscale0` к Tailscale-IP; остальные входящие подключения к локальному TCP/4180 блокируются до Docker DNAT, включая IPv6. Это закрывает обход обычных правил UFW опубликованными Docker-портами. Правила UFW сохранены. Исходные файлы и порядок проверки: [deploy](deploy/) и [доступ через Tailscale](docs/TAILSCALE_ACCESS.md).

## Новая установка и миграции

Нужны Docker Compose либо Node.js 22.12+ и PostgreSQL 16. Перед первым запуском:

```bash
cp -n .env.example .env
chmod 600 .env
mkdir -p var/uploads var/work
chmod 700 var/uploads var/work
# В .env укажите HOST, два разных случайных пароля и DATABASE_URL.
# Получить пароль: openssl rand -hex 24
# ADMIN_PASSWORD — минимум 12 символов; DATABASE_URL использует POSTGRES_PASSWORD.
docker compose -f compose.yml -f compose.postgres.yml up -d --wait db
docker compose -f compose.yml -f compose.postgres.yml build app maintenance
DB_MIGRATION_CONFIRM=donarium docker compose -f compose.yml -f compose.postgres.yml run --rm maintenance
docker compose -f compose.yml -f compose.postgres.yml up -d --wait app
```

Перед обновлением существующей БД создайте [резервную копию](docs/BACKUP.md). Мигратор проверяет имя отдельной БД DONARIUM, явный флаг, checksum уже применённых SQL и дубли файловых связей перед миграцией 002. Каждая миграция транзакционная. Оригинальные файлы миграции не меняют. Миграция 002 пересоздаёт только вычисляемые поисковые поля и индексы; на большой БД обновление следует выполнять при остановленном приложении.

У файлов `var/uploads` и `var/work` должен быть владелец UID 1000 — пользователь `node` контейнера. На обследованном сервере это совпадает с UID владельца checkout. Для хоста с другим UID настройте владельца только этих каталогов.

## Внешняя библиотека

В текущей установке библиотека .141 настроена через `compose.nfs.yml`; порядок ниже относится к новой установке с другими корнями. В шаблоне `STORAGE_ROOTS=[]`: разрешено только управляемое хранилище загрузок. Подключение оригиналов — одноразовая настройка сервера:

1. Скопируйте `compose.storage.example.yml` в `compose.storage.yml` и укажите настоящий `source`.
2. Задайте в `.env` логический ключ и **контейнерный** путь, например:

   ```dotenv
   STORAGE_ROOTS=[{"key":"MODELS","name":"Модели","path":"/library/models"}]
   ```

3. Пересоздайте приложение, включив файл с монтированием:

   ```bash
   docker compose -f compose.yml -f compose.postgres.yml -f compose.storage.yml up -d app
   ```

Параметры `MANAGED_STORAGE_ROOT` и `WORK_ROOT` задают физические host-каталоги Docker bind mounts и могут указывать на отдельные диски. Внутри контейнера пути остаются `/app/var/uploads` и `/app/var/work`. Новые host-каталоги нужно создать заранее и предоставить UID1000 доступ.

При последующих запусках используйте те же три `-f`. Внешние bind mounts работают read-only, `create_host_path:false` защищает от случайного создания пустой папки вместо библиотеки. Не меняйте ключ корня без переноса метаданных: по нему восстанавливаются файловые связи. Для запуска без Docker укажите настоящие абсолютные пути Ubuntu в `STORAGE_ROOTS`.

Все повседневные операции доступны в интерфейсе: каталог, карточка, импорт папок, экспорт/восстановление, настройки/состояние. Приложение не следует символическим ссылкам. Неподключённый или отсутствующий оригинал отмечается в карточке.

## Перенос и backup

CSV содержит строки товаров, а категории, теги и связи — явные JSON-массивы в отдельных колонках. JSON содержит структурированные таблицы. Эти выгрузки сохраняют метаданные, но не включают оригиналы.

ZIP v2 содержит `manifest.json` и таблицы NDJSON, включая независимый реестр и источники импорта. Для большой библиотеки используйте ZIP метаданных без оригиналов. Полный ZIP дополнительно содержит `files/<file-id>/<name>` — каждый registry file один раз; размер экспорта/восстановления ограничен 4 ГиБ. Указаны версия схемы, количества и SHA-256. При восстановлении архив сначала распаковывается в изолированный staging, проверяется и показывается preview. После подтверждения метаданные фиксируются транзакционно, файлы попадают в управляемое хранилище. Выбор конфликта: пропустить существующий товар или создать копию с новым ID и пустым конфликтующим SKU. Существующие записи не перезаписываются. Если локальный оригинал отсутствует, полный экспорт завершается ошибкой.

Для текущей библиотеки сохраняйте PostgreSQL custom dump и metadata ZIP отдельно от файлов; оригиналы резервируйте на другой физический диск/сервер. Не создавайте tar/ZIP на 394 ГиБ вместе с распакованной копией на рабочем HDD. Скрипт для небольших корней и команды восстановления: [docs/BACKUP.md](docs/BACKUP.md). Спецификация обмена: [DATA_PORTABILITY.md](DATA_PORTABILITY.md).

## Разработка и проверки

```bash
npm ci
# Для запуска с хоста DATABASE_URL должен указывать на 127.0.0.1:5548.
npm run dev
npm run typecheck
npm run build
npm test
npm run test:integration
```

На обследованном хосте системный Node.js 20 оставлен без изменений. Проверки выполнялись с `/tmp/donarium-tools/node` v22.23.2:

```bash
PATH=/tmp/donarium-tools:$PATH npm run typecheck
PATH=/tmp/donarium-tools:$PATH npm run build
PATH=/tmp/donarium-tools:$PATH npm run test:integration
```

`test:integration` создаёт отдельный Compose-проект `donarium-audit-test`, две БД на loopback-порту 5549 и временные схемы/файлы. Рабочая БД не очищается и не используется. Без `TEST_DATABASE_URL` PostgreSQL-проверки честно пропускаются. Для завершения временного окружения: `node scripts/test-integration.mjs --down`.

Браузерные проверки с настоящей тестовой БД:

```bash
# Node 22+, подготовленный test:integration и установленный Chromium:
npm run build
TEST_DATABASE_URL=postgresql://donarium_test@127.0.0.1:5549/donarium_test_source \
  E2E_WRITE=donarium_test \
  E2E_PASSWORD=donarium-browser-test-password \
  npm run test:e2e
```

Playwright сам запускает свежий QA-сервер на loopback:4196, создаёт схему и временные корни, затем очищает их через SIGTERM. Ручной сервер на этом порту перед прогоном нужно завершить; повторное использование исключено. Если нужен системный Chromium, задайте PLAYWRIGHT_CHROMIUM_EXECUTABLE. Write-сценарии запрещены для production URL. [Независимый аудит](docs/INDEPENDENT_AUDIT_2026-10-28.md) · [Прежние проверки](docs/VERIFICATION.md) · [Архитектура](ARCHITECTURE.md).

## Практические границы

- Библиотека .141 содержит 607 проверенных архивов. Привязки к товарам подтверждает владелец; автоматического применения по имени нет.
- Нет обратного импорта произвольных CSV/JSON; восстановление реализовано для ZIP DONARIUM v1 и v2, включая ZIP метаданных.
- Preview сканирования папок хранится в памяти и повторяется после перезапуска. Подтверждённые папки фиксируются по одной; повторное сканирование продолжает работу без дублей.
- Полный ZIP требует места под архив и распаковку и ограничен 4 ГиБ. Для библиотеки .141 используйте экспорт метаданных и отдельное резервирование оригиналов.
- Проверки проходили на небольших fixtures; нагрузка в сотни тысяч товаров и терабайты файлов не измерялась. Используется OFFSET-пагинация.
- Для обычного HTTP в доверенной LAN cookie `Secure` выключен. При локальном HTTPS задайте `SECURE_COOKIE=true`. Смена пароля/перезапуск завершает сеансы.

Исправления ещё не развёрнуты в рабочем контейнере. Recovery повторяет неудачные старты NFS; обычный stop отменяет текущий retry, но не защищает от будущего OnFailure.
