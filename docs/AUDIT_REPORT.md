# DONARIUM — итог аудита и реализации

Исторический отчёт о состоянии на 24.10.2026. Текущее состояние и новые проверки: [технический аудит 28.10.2026](TECHNICAL_AUDIT_2026-10-28.md).

24 октября 2026 года. Изменён существующий проект, сохранены React/Fastify/PostgreSQL и визуальная основа. Рабочий адрес: **http://192.168.0.151:4180**. Внешние папки не подключались по прямому указанию владельца.

## 1. Аудит

Первоначально работали чтение каталога, поиск, категория, пагинация, карточка и health. Production использовал шесть явных демонстрационных записей. PostgreSQL-адаптер и мигратор существовали, но операций записи, файлового сервиса, импорта/экспорта и пароля владельца не было. SKU был обязательным. Профиль, коллекции, история и их экспорт работали только в localStorage и не представляли серверный каталог. Пользовательских таблиц, ролей и организаций в БД не найдено.

Сильные стороны сохранены: параметризованный SQL, pg_trgm/GIN, серверная пагинация, миграции с checksum/транзакциями/advisory lock, отдельная инфраструктура DONARIUM, адаптивные компоненты.

## 2. Очистка

Удалены `Dashboard.tsx`, `WorkspacePages.tsx`, `workspace.tsx`, маршруты профиля/избранного/коллекций/истории, чаепитие, браузерный экспорт личного пространства и связанные неиспользуемые стили. Удалён неработавший параметр `EXTERNAL_STORAGE_BASE_URL`. Существующие записи БД и localStorage пользователя не очищались. Исходник пользовательского баннера и PDF сохранены как материалы владельца.

Деморепозиторий остаётся явным read-only fixture для тестов, без автоматического переключения при отказе PostgreSQL. Рабочая установка переведена на PostgreSQL, без seed. Нужных зависимостей старого приложения удалять не потребовалось; добавлены только `sharp`, `yazl`, `yauzl` и их TypeScript-типы.

## 3. Архитектура

Один Fastify-процесс отдаёт React и API, проверяет пароль владельца, обслуживает файлы и ограниченные фоновые задачи. PostgreSQL хранит каталог и связи. `storage` отвечает за разрешённые корни и файловые операции, `transfer` — за независимый формат и восстановление. Redis, брокеров, облаков, пользователей и ролей не добавлено. Подробности: [ARCHITECTURE.md](../ARCHITECTURE.md).

## 4. Работающие возможности

Через браузер доступны CRUD карточек, nullable SKU, описание, фотографии и обложка, категории, теги, статусы, поиск без учёта регистра с кириллицей/латиницей, фильтры и сортировки, URL-состояние и серверная пагинация. Фотографии используют WebP-миниатюры и lazy loading.

Реализованы файловый браузер, привязка существующих файлов/папок без копирования, потоковая загрузка с SHA-256, отдельное скачивание и ZIP64 карточки, проверка отсутствующих файлов и отвязка. Импорт папок выполняет сканирование в фоне, preview, выбор/подтверждение, необязательную категорию и отчёт. Повторный импорт обновляет связи без дубликатов. Вручную связанные файлы тоже распознаются; неоднозначные случаи блокируются и показываются как ошибки. Выбор повторно проверяется в транзакции.

## 5. База данных

Основные таблицы: `products`, `categories/product_categories`, `tags/product_tags`, `storage_locations`, `assets`, `import_sources`. Исходные `external_links` сохраняют независимые внешние IDs. Служебные `schema_migrations` и `transfer_receipts` отслеживают схему и успешные восстановления.

`001_initial.sql` не менялась. `002` добавляет nullable SKU, статус, обложку, origin и идемпотентные источники; пересоздаёт только вычисляемые поисковые поля. `003` сохраняет экспортированные даты при восстановлении и добавляет lower-title index. `004` фиксирует receipt COMMIT. `005` добавляет индекс поиска файловых связей. При старых duplicate links preflight002 безопасно останавливает миграцию; ручной разбор после backup описан в BACKUP.md.

Создана новая отдельная рабочая БД `donarium` в контейнере `donarium-db-1`, применены001–005. Начальный каталог пустой: демонстрационные записи не выдаются за пользовательские. Существующие производственные товары не удалялись.

## 6. Файловая система и безопасность

Управляемые файлы: host `var/uploads`, временные операции: `var/work`. Пути задаются `.env` и bind mounts; их можно перенести на ёмкий диск. В контейнере используются `/app/var/uploads` и `/app/var/work`. Внешние корни сейчас отсутствуют (`STORAGE_ROOTS=[]`); это согласованный пропуск настройки, а не заглушка файлового сервиса.

Внешние оригиналы монтируются read-only и остаются на месте. БД хранит логический ключ/UUID и относительный путь. Удаление карточки/отвязка никогда не удаляет физические оригиналы, включая uploads. Symlink/traversal/специальные файлы запрещены; Ubuntu открывает компоненты через directory FD и `O_NOFOLLOW`. Корни не опубликованы как static.

API, файлы и экспорт защищены одним паролем, без регистрации. Сессии HttpOnly/SameSite=Strict,12 часов, process-local; есть Origin-проверка изменений и ограничение попыток входа. Пароль сгенерирован и сохранён только в локальном `.env` (`ADMIN_PASSWORD`), права0600. Он не выводился в логи. Доступ в интернете не публиковался, SKUFnya не изменялась.

## 7. Экспорт, восстановление и backup

CSV содержит основные поля и однозначные JSON-массивы категорий/тегов/ресурсов, защищает табличные формулы. JSON потоково сохраняет структурированные таблицы с версией. Полный ZIPv1 содержит manifest,7 NDJSON-таблиц и неизменённые файлы; у таблиц и файлов SHA-256. Абсолютных исходных путей серверов в переносимой структуре нет. HTTP-ссылки сохраняются без сетевого скачивания.

Restore проверяет версию, пути, типы ZIP-записей, лимиты, IDs, ссылки, принадлежность обложки, размеры и hashes до подтверждения. `skip` сохраняет существующие карточки, `copy` создаёт новые UUID и сбрасывает конфликтующий SKU. Метаданные фиксируются атомарно; перемещение файлов откатывается при ошибке. Receipt позволяет согласовать перезапуск и потерю ответа успешного COMMIT. Исходный ZIP следует хранить до проверки результата.

Backup-скрипт создаёт PostgreSQL custom dump и tar каждого корня с SHA-256. Он проверен восстановлением отдельной тестовой БД и файла. Перед переключением создан `backups/initial-postgres-20261024`; сохранён прежний образ `donarium-app:before-library-audit-20261024` и прежний `.env` в backups. Данные и команды восстановления: [DATA_PORTABILITY.md](../DATA_PORTABILITY.md), [BACKUP.md](BACKUP.md).

## 10. Ограничения

- Реальные внешние каталоги владельца пока не подключены по его просьбе; объём, права и содержимое не проверялись.
- Обратный импорт произвольных CSV/JSON не реализован; восстановление работает с ZIP DONARIUMv1.
- Сканирование: до200000 просмотренных элементов,10000 кандидатов,10000 файлов в одной папке; большие деревья импортируются частями. Его preview теряется при рестарте, подтверждённые папки фиксируются по одной.
- Нет измерений на100000+карточек и терабайтах. Используется OFFSET-пагинация, проверка идентификаторов archive требует RAM пропорционально их числу.
- Полный ZIP требует дополнительного диска; restore хранит uploadZIP и extractedfiles. На разделе проекта около24ГБ свободно: для большой библиотеки нужен другой диск, настраиваемый через env/bind mounts.
- Проверен LAN-IP с самого сервера и mobile viewport Chromium; отдельный физический телефон/ПК не проверялся.
- На plain HTTP LAN нет шифрования транспорта; локальный HTTPS потребует соответствующей настройки и `SECURE_COOKIE=true`.
- Приложение не следит непрерывно за внешними изменениями файлов. Повторный импорт/проверка доступности актуализируют связи; удалённые с диска ресурсы показываются отсутствующими.

## 11. Наиболее полезное развитие

Подключить настоящую библиотеку и отдельный ёмкий диск; настроить регулярный backup с проверкой восстановления. Затем измерить поиск/сортировку и deep-page запросы на реальном объёме и по результатам рассмотреть cursor pagination. Если практический обмен потребует, добавить mapping/preview произвольного CSV/JSON. Новые сервисы и многопользовательская архитектура для этого не нужны.
