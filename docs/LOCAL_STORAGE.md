# Локальное хранилище Donarium

Donarium 0.3.0 и схема 006 развёрнуты с согласия владельца 27 октября 2026. Все соответствия оставлены для ручного подтверждения. Состояние внедрения фиксируется в `docs/STORAGE_IMPLEMENTATION_REPORT.md`.

## Диск и NFS

Приложение остаётся на .151. Архивы, загрузки и рабочие файлы находятся на ext4 .141, UUID `76d90fb2-6d59-4fdb-8280-81154e6c93d9`. Исходный каталог `/srv/data/google-drive/Идеально` сохраняется. `/srv/data/donarium/library` — read-only bind mount этого каталога. Так сохраняются имена, inode и содержимое без перемещения/копирования 394 ГиБ. Добавляется только скрытый идентификатор диска; архивы не изменяются.

`deploy/storage/setup-server.sh` вместе с `configure-nfs-exports.sh` и `allow-docker-nfs-traverse.py` запускается владельцем на .141 через sudo. Скрипты должны находиться в одном каталоге. Он сохраняет конфигурацию в `donarium/backups`, устанавливает NFS, делает экспорты только для .151 с `root_squash`, `sync`, отдельными ro/rw правами, проверкой UUID и зависимостью от `srv-data.mount`. Экспорт использует ограниченный псевдокорень `/srv/data/donarium/.exports` и четыре настоящих bind mount дочерних представления: обычные вложенные каталоги одного ext4 не используются для разделения ro/rw. Данные остаются в library/uploads/work/inventory без копирования. Параметр export `mountpoint=/srv/data` проверяет физическое монтирование; конкретные bind mounts дополнительно проверяет systemd guard по mount ID и UUID. Голый `mountpoint` для bind mount того же ext4 не используется: встроенная stat-проверка nfs-utils не распознаёт его. Отдельная таблица nftables ограничивает только порт NFS, не меняя остальные таблицы. При активном UFW добавляется узкое разрешение .151 TCP/2049.

`deploy/storage/setup-client.sh` запускается владельцем через sudo на .151. Он подключает `library`, `uploads`, `work`, `inventory` в `/mnt/donarium` через NFSv4.2, TCP, `hard,nosuid,nodev,noexec`. Под немонтированными каталогами права root:root 000. Скрипт проверяет маркеры от UID 1000 и выполняет пробную запись только в uploads. Для bind mount Docker daemon используется согласованный адресный ACL UID 65534 с единственным правом `--x` на четырёх корнях; права other и вложенных файлов не расширяются. Контейнеры и `.env` не переключаются.

`compose.nfs.yml` — отдельный override к двум существующим compose-файлам. Он подключает NFS через bind mounts с `create_host_path: false`. `STORAGE_REQUIRE_GUARDS=true` требует проверки типа ФС, точного источника NFS и маркера диска перед файловыми операциями. Ни один отсутствующий mount не заменяется каталогом системного диска. `deploy/storage/donarium.service` упорядочивает запуск только Donarium после mounts, не перезапуская другие приложения или весь Docker.

Основания: [exports(5), mountpoint и root_squash](https://www.man7.org/linux/man-pages/man5/exports.5.html), [nfs(5), hard mount](https://www.man7.org/linux/man-pages/man5/nfs.5.html), [systemd, зависимости mount units](https://www.freedesktop.org/software/systemd/man/257/systemd.mount.html).

## Схема и API

Миграция `006_storage_registry.sql` добавляет `storage_files`, `storage_operations`, `storage_events`, `storage_matches`, `storage_uploads`, а также `assets.file_id`, `metadata`, `retired_at`. Старые UUID, столбцы и URL `/api/v1/assets/:id/download|content|thumbnail` сохраняются. Триггер связывает и старые импортеры с реестром. Один путь соответствует одной записи реестра, один файл используется несколькими карточками. Регистр пути значим. Индекс SHA-256 не уникален: разные физические оригиналы не удаляются и не объединяются автоматически.

Новый API (за существующей авторизацией):

- `GET /api/v1/files`: поиск по имени/SHA-256, фильтры root, format, status, unlinked, duplicates, пагинация.
- `GET /api/v1/files/:id`: товары и файлы с одинаковой контрольной суммой.
- `GET /api/v1/files/:id/download`: потоковое чтение и HTTP Range.
- `PUT /api/v1/files/upload?name=...`: бинарная потоковая загрузка.
- `POST /api/v1/products/:id/files` с fileId: идемпотентная привязка.
- `PUT /api/v1/products/:id/assets/:assetId/file`: замена с сохранением UUID вложения и предыдущей связи в истории.
- Существующий DELETE вложения удаляет только связь; файл остаётся в реестре.
- `POST /api/v1/files/inventory`: регистрация всех обычных файлов корня без изменения содержимого. SHA-256 проверяется отдельной операцией.
- `POST /api/v1/files/verify` или `/files/:id/verify`: фоновая проверка размера и SHA-256; исходная контрольная сумма при порче не заменяется.
- `POST /api/v1/files/sync-checksums`: чтение описи .141 через read-only корень INVENTORY и сопоставление размера/mtime/ctime исходников.
- `/api/v1/storage/operations`: постоянный прогресс и результаты; PostgreSQL session lock исключает параллельные тяжёлые операции между процессами.
- `/api/v1/storage/uploads`: журнал загрузок, recovery помечает оставшиеся без активной блокировки процессы. DELETE разрешён только для временного фрагмента прерванной загрузки.

Загрузка сначала пишет в `.staging/<uuid>` на NFS, ограничивает размер и считает SHA-256. После fsync PostgreSQL advisory lock по содержимому сериализует дедупликацию. Проверенный существующий оригинал переиспользуется. Новый объект публикуется атомарной hard link в `objects/<prefix>/<sha256>`, без перезаписи. Сбой БД оставляет объект для последующей регистрации; оригиналы при ошибке COMMIT не удаляются. Строки upload intent и session locks отличают живые загрузки от прерванных. У приложения максимум две параллельные загрузки. Остатки staging не выдаются как готовые файлы.

## Миграция карточек

`/api/v1/storage/matches/preview` работает только с уже зарегистрированными файлами, не создаёт карточки и не привязывает архивы. Сохраняются исходные имена и снимок затрагиваемых полей. Имя с пометкой `(идеально)` не смешивается с именем без неё. Несколько исходных записей считаются согласованными только если все дают один и тот же UUID файла.

Подтверждение требует доступного файла с проверенным SHA-256. Даже точное имя не доказывает соответствие модели: решения подтверждает владелец. Нормализованные совпадения просматриваются отдельно. Повторное построение preview сбрасывает ещё не применённые решения, сохраняя применённые.

Применение `/matches/apply` обрабатывает только подтверждённые UUID. Оно проверяет снимок описания, источника и Drive-вложений, сохраняет существующий UUID вложения, переводит его на file_id, сохраняет происхождение, убирает активный Google Drive source_url и заменяет ссылки в описании. Дополнительные Drive-вложения остаются историческими, с retired_at. Данные Notion в external_links остаются историческими.

Откат `/matches/:id/rollback` выполняет сравнение с применённым снимком. Если пользователь изменил затрагиваемые поля/связи, откат останавливается. Изменения названия, категорий и прочих незатронутых полей сохраняются. Массовое восстановление старого pg_dump поверх работающей БД для отката не используется.

Репетиция на восстановленной копии выполняется `node --import tsx scripts/prepare-storage-report.ts`. Скрипт жёстко ограничен проверенной тестовой БД backup. Первоначальный отчёт: `backups/storage-registry-20261027/migration-preview.json`. Финальная репетиция на реальных NFS mounts: `node --import tsx scripts/rehearse-nfs-storage.ts backups/storage-cutover-20261027193741Z`. Результат сохраняется рядом с проверенным backup в `nfs-rehearsal.json`. HTML/CSV для просмотра создаёт `scripts/storage-review-report.py`, принимающий JSON репетиции и опись SHA-256.

## Экспорт, восстановление и резервирование

ZIP метаданных v2 включает каталог, категории/теги/связи, реестр файлов, import_sources, external_links и журналы миграции. Ссылки на файлы — UUID, логический ключ и относительный путь. Конфигурация серверов и абсолютные пути хранилищ в структуру привязок не входят. Исторические поля происхождения могут содержать старые пути как сведения об импорте, а не рабочие ссылки.

Экспорт без оригиналов: `POST /api/v1/exports/metadata`, затем существующий endpoint скачивания transfer job. В интерфейсе: «Экспорт и восстановление» → «Метаданные ZIP для восстановления». Это основной формат для большой библиотеки .141.

Полный ZIP v2 включает каждый registry file один раз, даже если он связан с несколькими товарами. Экспорт и загрузка ZIP для восстановления ограничены 4 ГиБ, чтобы не создавать ещё одну 394-ГиБ копию. Восстановление проверяет checksum таблиц/файлов и все связи, сохраняет UUID, проверяет подключённые оригиналы в фоне. Отсутствующие корни выводятся в preview; записи могут быть восстановлены как unavailable и проверены после подключения. Старый ZIP v1 по-прежнему восстанавливается в пределах лимита. Повторное восстановление v2 проверяет и переиспользует существующий оригинал, удаляя только временную распакованную копию. При конфликте содержимого существующего UUID или недоступном оригинале операция останавливается без его перезаписи. Повторный импорт с пропуском не перезаписывает существующие карточки. Режим копирования создаёт новые UUID карточек, переиспользуя файлы.

Для переноса метаданных на другой сервер подключите тот же .141 и логические ключи LIBRARY/DONARIUM_UPLOADS/INVENTORY. При изменении IP приложения замените разрешённый клиент в NFS exports и NFS firewall на .141; прежнее приложение перед переключением остановите. UUID файлов и связи в БД менять не требуется. Настройте STORAGE_GUARDS под пути нового контейнера, а не меняйте пути в карточках. Выполните проверку целостности и контрольное скачивание после восстановления.

Файлы резервируются на **другой физический диск/сервер**, отдельно от ZIP метаданных. Пример команды с предварительным просмотром (подставьте существующий backup target):

```bash
rsync -aHAXn --checksum --exclude=/.exports/ --protect-args /srv/data/donarium/ /path/on/independent-backup/donarium/
```

После проверки назначения уберите `n`; не используйте `--delete` без отдельного согласования. Для library bind mount используйте запуск с уже подключённой library либо резервируйте исходный `google-drive/Идеально/` отдельно. Сохраните файл описи SHA-256 и проверьте восстановленную копию. Каталог backups на том же HDD полезен для конфигурации и журналов, но не является независимой защитой от отказа HDD.

## Ввод в эксплуатацию

Первое переключение выполнено. Ниже сохранён порядок для новой установки/повторного внедрения; повторно выполнять рабочую миграцию и preview для продолжения ручной проверки не требуется.

1. Проверить fresh pg_dump, SHA-256 и реальное восстановление. `scripts/verify-storage-backup.mjs` создаёт новую БД только в изолированном контейнере donarium-audit-test.
2. Подключить NFS двумя подготовленными скриптами. Проверить read-only library, запись uploads, root_squash, отсутствие local fallback и старт mount units.
3. Скопировать uploads на .141 с сохранением исходников .151; проверить каждый размер/SHA-256 по backup manifest (`scripts/verify-storage-copy.py`). Перед финальным переключением повторить инкрементальную синхронизацию в коротком окне остановленных записей.
4. После согласования остановить только Donarium app, сделать fresh backup, применить транзакционную миграцию 006, запустить заранее собранный образ с compose.nfs.yml и системным unit. БД не пересоздавать, volume не удалять.
5. Зарегистрировать library, проверить uploads, загрузить готовые SHA-256 из описи сервера. Опись хранит mtime/ctime в десятичных строках наносекунд, чтобы JSON/JavaScript не округляли их. Приём SHA требует точного совпадения размера и обоих времён с BigInt stat через NFS. Вычисление полной описи можно возобновлять: `scripts/library-inventory.py` проверяет stat и fsync-ит результат каждого архива.
6. Построить preview, подтвердить проверенные соответствия, применить их и скачать контрольные файлы по старым asset UUID. Пять неизвестных товаров оставить без сомнительной привязки, 14 невыбранных архивов доступны в фильтре непривязанных.
7. Проверить перезапуск **Donarium**, восстановление metadata ZIP и состояние mounts. Перезагрузку серверов и отключение сети согласовать отдельно; отсутствие диска уже проверяется тестом fail-closed, но реальное отключение требуется проверить после установки инфраструктуры.

Откат релиза: вернуть сохранённый предыдущий image с теми же NFS логическими корнями. Добавочная схема совместима со старым API. Для постоянного отката задайте сохранённый прежний image в DONARIUM_STORAGE_IMAGE локального .env, сохранив COMPOSE_FILE с NFS override и текущие NFS mounts. Пользовательские метаданные не откатывать через старый dump. Решения сопоставления отменяются поштучно через CAS-откат; файлы физически сохраняются. Копию .151 не удалять до завершения проверки и отдельного решения владельца.


## Позднее включение файлового сервера

Если .151 загрузился раньше .141, первая попытка mount ограничена 90 секундами. Без повторного запуска приложение оставалось остановленным даже после появления NFS. `deploy/storage/enable-storage-recovery.sh` устанавливает OnFailure для четырёх mount units и `donarium-storage-recover.service`. Служба пытается запустить Donarium повторно через 30 секунд после неудачи; его прежние Requires/BindsTo по-прежнему требуют NFS. ExecCondition прекращает восстановление для отключённого donarium.service. Обычная ручная остановка при здоровых mounts не запускает recovery.

Установщик сохраняет прежние units/drop-ins и не меняет БД, физические файлы, NFS exports или другие приложения. Для применения на .151: `sudo bash /home/hpelitdesk/apps/Donarium/deploy/storage/enable-storage-recovery.sh`. Включение production service теперь устанавливает recovery автоматически.

Регрессионная проверка: `python3 scripts/verify-storage-recovery.py`. Она использует только собственные временные user units: недоступная зависимость → повтор → поздняя готовность → запуск; отдельно проверяет ручную остановку. Рабочие mounts не отключаются.
