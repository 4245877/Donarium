# Donarium: файловое хранилище — состояние на 28 октября 2026

**27 октября развёрнут Donarium 0.3.0 с рабочим NFS-хранилищем и схемой 006.** Перезапуск контейнера и работа приложения после установки systemd проверены. Все соответствия оставлены для подтверждения владельцем, согласно его выбору.

**Утром 28 октября выявлен отдельный сбой загрузки:** .151 включился раньше .141, четыре NFS mount превысили таймаут, Donarium остался остановлен. Сервер .141 и правильный HDD доступны. Исправление повторного запуска применено владельцем и проверено: NFS подключён, Donarium active/healthy, локальный архив читается через HTTP Range. Данные и все решения пользователя сохранены.

## 1. Что реализовано

Независимый реестр физических файлов, потоковая загрузка на .141, SHA-256, атомарная публикация, предотвращение дополнительных копий при параллельных одинаковых загрузках. Один файл используется несколькими товарами; замена сохраняет UUID вложения, отвязка сохраняет оригинал. Есть поиск, фильтры непривязанных, отсутствующих, повреждённых и одинаковых по содержимому файлов, журнал загрузок, recovery временных фрагментов, фоновые проверки и прогресс.

В Donarium добавлен раздел «Файлы» и доработаны карточки: загрузка, выбор существующего файла, скачивание, замена и отвязка. Старые файловые URL по UUID сохранены. Для прежнего Drive-вложения показывается необходимость локального сопоставления; ссылки Drive не предлагаются как кнопки скачивания моделей.

Сопоставление имеет предпросмотр, отдельное подтверждение и применение только выбранных подтверждённых решений. Снимки и журнал сохраняют происхождение; откат сравнивает затрагиваемые поля и останавливается при конфликте с пользовательскими правками.

ZIP метаданных v2 переносит товары, категории, связи, реестр, источники и журналы без оригиналов. Полный ZIP включает каждый registry file один раз; размер ограничен 4 ГиБ, чтобы не создавать дополнительную копию библиотеки 394 ГиБ. Восстановление старого v1 поддерживается.

## 4. Серверные настройки

Приложение остаётся на .151. Файлы находятся на .141, `/srv/data` → `/dev/sda1`, ext4, UUID `76d90fb2-6d59-4fdb-8280-81154e6c93d9`. UID/GID приложения и miha: 1000:1000.

`/srv/data/donarium/library` представляет исходный `/srv/data/google-drive/Идеально` через read-only bind mount. Оригиналы не перемещены: сохранены прежний путь, имена, inode и содержимое без копирования 394 ГиБ. Карточки используют логические ключи и относительные пути.

NFSv4: отдельный псевдокорень `.exports`, доступ только .151, `root_squash`, `sync`, rw uploads/work и ro library/inventory. Экспорт и systemd guard зависят от правильного HDD и bind mounts. Отдельный firewall ограничивает порт NFS. Клиентские mounts в `/mnt/donarium` используют `hard,nosuid,nodev,noexec`; под немонтированными каталогами root:root 000. Docker bind mounts не создают отсутствующие каталоги.

По отдельному разрешению добавлен только адресный ACL UID 65534 `--x` на четырёх корнях. Права other и вложенных файлов не расширены; прежние ACL сохранены в backup. Из контейнера проверены root_squash, запрет записи в library, запись/fsync/атомарная публикация в uploads и отказ при неверном маркере до mkdir.

Служба `donarium.service` установлена и включена владельцем; пересоздаёт только app после NFS. Остальные приложения и production PostgreSQL при переключении не перезапускались. Исправление 28 октября добавляет OnFailure для mount units и `donarium-storage-recover.service`: повтор каждые 30 секунд после неудачного запуска, с прежними защитами и без отмены обычной ручной остановки приложения.

- Исправление утреннего старта применено: четыре OnFailure и recovery unit установлены, Donarium восстановлен. Recovery завершился успешно; обычная ручная остановка остаётся доступна.
- Завершить дополнительную проверку файлов восстановленной тестовой БД после повторного подключения защищённых NFS-корней. Проверки исходников и production уже выполнены; это отдельная завершающая проверка переносимости.
- Все решения по соответствиям оставлены владельцу. Особенно требуют просмотра 160 нормализованных и 5 отсутствующих. Точное имя также не доказывает тождество содержимому Google Drive.
- Независимая копия всей библиотеки на другом носителе отсутствует: назначение не предоставлено. Backup конфигурации и описи на том же HDD не защищают от физического отказа диска.
- Отключение сети во время активной загрузки в production специально не выполнялось. Проверены guards и восстановление операций; утренняя реальная перезагрузка выявила описанный случай позднего появления сервера.

## 8. Действия владельца

Дополнительных sudo-действий для выполненного переключения не требуется. Исправление старта уже установлено; backup прежних units: `backups/storage-boot-recovery-20261028T075345Z`. В native host backup-настройках исправлены MANAGED_STORAGE_ROOT/WORK_ROOT: новые резервные копии читают текущие NFS-каталоги, а не старую копию .151.

Для миграции карточек откройте «Файлы» → выберите «Архивы моделей» → «Сопоставление товаров». Просмотрите исходное имя и архив, подтвердите выбранный файл либо выберите другой. Затем отфильтруйте состояние «Подтверждены», отметьте нужные строки и нажмите «Применить подтверждённые». Повторное построение preview сбрасывает ещё не применённые решения; для обычного продолжения проверки используйте обновление списка.

Для пяти товаров без кандидата нужен ручной выбор или загрузка подходящего оригинала. Для независимого backup нужен другой диск/сервер достаточной ёмкости; порядок описан в `LOCAL_STORAGE.md`.
