# Donarium: доступ через LAN и Tailscale

Настроено на сервере `miha` 25 октября 2026 года.

| Сеть | Адрес |
| --- | --- |
| Tailscale, в том числе Windows `100.107.202.105` | http://100.91.30.10:4180 |
| LAN `192.168.0.0/24` | http://192.168.0.151:4180 |

## Причина и исправление

Приложение было здоровым, но Docker публиковал TCP/4180 только на
`192.168.0.151`. Поэтому подключения к `100.91.30.10` и `127.0.0.1`
отклонялись. Tailscale до Windows работал; отсутствие правила UFW для 4180
не являлось причиной отказа: Docker принимал опубликованный трафик до
цепочек UFW, а `DOCKER-USER` была пустой.

В `compose.yml` добавлена отдельная привязка из `TAILSCALE_IP`, в `.env`
установлено `TAILSCALE_IP=100.91.30.10`. Существующая LAN-привязка сохранена.
Без `TAILSCALE_IP` дополнительная привязка использует `127.0.0.1`.
Wildcard-привязок и публикации по IPv6 нет. PostgreSQL остался на
`127.0.0.1:5548`.

Установлены два новых файла с владельцем `root:root` и правами `0644`:

- `/etc/ufw/donarium-4180.nft` — копия [правил](../deploy/donarium-4180.nft).
- `/etc/systemd/system/donarium-4180-firewall.service` — копия
  [unit-файла](../deploy/donarium-4180-firewall.service).

Сервис включён в автозагрузку. Он загружает отдельную таблицу
`inet donarium_4180` после UFW, до `network-pre.target` и `docker.service`.
Правила проверяют входящий TCP/4180 к локальным адресам в `prerouting`
с приоритетом `-110`, до Docker DNAT с приоритетом `-100`:

- `eno1`, источник `192.168.0.0/24`, назначение `192.168.0.151` — разрешён.
- `tailscale0`, источник `100.64.0.0/10`, назначение `100.91.30.10` — разрешён;
  доступ также ограничивается действующей политикой Tailscale.
- Локальный трафик сервера разрешён.
- Прочие входящие пакеты к локальному TCP/4180 блокируются, включая IPv6.

Разрешённые пакеты продолжают проходить существующие фильтры. Правила
Docker, Tailscale и UFW не заменяются. Повторная загрузка атомарно заменяет
только таблицу Donarium. Изменение сетевых адресов/интерфейса требует
согласованного обновления `.env` и установленного nft-файла.

Обход UFW опубликованными портами описан в
[документации Docker](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

## Резервная копия и обслуживание

Закрытый каталог резервной копии (`0700`):
`/home/hpelitdesk/apps/Donarium/backups/network-20261025T165319Z`.
В нём сохранены исходные `compose.yml`, `.env`, `.env.example`, `README.md`,
архив исходной конфигурации UFW, снимки iptables/nft, контейнеров и результаты
сравнения `audit-results.json`. `.env` с паролями имеет права `0600`.
Новые файлы хоста до изменения отсутствовали; это записано в
`new-host-files.txt`.

Обычная проверка:

```bash
docker compose -f compose.yml -f compose.postgres.yml ps
docker port donarium-app-1
curl --noproxy '*' -f http://100.91.30.10:4180/health
curl --noproxy '*' -f http://192.168.0.151:4180/health
systemctl status donarium-4180-firewall.service
sudo nft list table inet donarium_4180
```

Для изменения ограничений сначала сохранить установленный nft-файл,
проверить новый через `sudo nft --check -f /etc/ufw/donarium-4180.nft`,
затем выполнить `sudo systemctl reload donarium-4180-firewall.service`.
Перезагрузка UFW/Docker для этого не требуется.

Для возврата к прежней LAN-привязке восстановить только `.env` и
`compose.yml` из резервной копии, сохранить `.env` с правами `0600`, затем
пересоздать только `app` с `--no-deps --no-build --pull never`.
Защиту порта можно оставить включённой. Для полного удаления новой защиты
администратор отключает только `donarium-4180-firewall.service`, удаляет
только таблицу `inet donarium_4180` и два новых файла хоста, затем
перечитывает unit-файлы. Остановка сервиса сама по себе таблицу не удаляет.
Восстанавливать весь снимок iptables или сбрасывать UFW не требуется.
